# Database Architecture

Target scale: 5,000 universities · 500,000 instructors · hundreds of millions of
activity records.

**How to read the numbers in this document.** Two separate measurement sessions
are quoted, and they are labelled throughout rather than blended:

- **Phase-10 dataset** — 100 universities / 10,000 instructors / 3.9M activity
  logs / 760 MB, generated by [prisma/perf-seed.sql](prisma/perf-seed.sql).
  Reproducible. Source of the dashboard-query figures in §6.
- **Pagination pass** — a smaller, targeted bulk load (20k activity rows for one
  instructor; 20,514 instructor rows) used to measure the two pagination indexes
  in §5. Not the same dataset, not interchangeable with the above.

Neither set was re-measured when this document was last revised. Anything not
measured is marked as such rather than estimated.

Verified against the live schema and both running Postgres containers on
2026-08-14.

## 2. Data model

**31 models, 18 enums**, grouped by concern:

```
IDENTITY     User · Manager · Instructor · Session
TENANCY      University · UniversitySettings · UniversityWorkingHours
             UniversityHoliday · BreakPolicy
ACADEMIC     Department · Program · Course · AcademicTerm · CourseAssignment
SCHEDULING   Schedule · ScheduleSlot
WORKFORCE    ActivityType · ActivityLog · LeaveRequest · WorkloadTarget
DELIVERABLES Deliverable · DeliverableLog
ANALYTICS    InstructorDailyMetric · InstructorWeeklyMetric
             UniversityDailyMetric
AI           AiInsight
REPORTING    ReportingPeriod · ReportJob · MetricsJobRun
SYSTEM       Notification · AuditLog
```

Deliberate modelling decisions, each still true of the current schema:

- **Opening/closing are generalised activities, not their own table**, enforced
  by a partial unique index on `(instructorId, workDate, activityTypeId) WHERE
  isOncePerDay = true`. See §8 for an important caveat about where that index is
  declared.
- **`DeliverableLog` carries its own `universityId` and `instructorId`** rather
  than reaching them through `Deliverable`. Denormalised deliberately — the
  schema comment states it directly: "a tenant-scoped query must not require a
  join to be safe."
- **Metrics are stored as integer minutes**, not float hours — summing millions
  of floats accumulates drift.
- **`AiInsight.universityId` is nullable** because `PLATFORM`-scoped insights
  have no tenant.

## 3. Tenant boundaries

`universityId` is the tenant key. Its nullability is not uniform, and the
difference is load-bearing:

**Required (`String`)** — the tenant-owned tables:
`UniversityWorkingHours`, `UniversityHoliday`, `Manager`, `Instructor`,
`LeaveRequest`, `ActivityLog`, `Deliverable`, `DeliverableLog`,
`UniversitySettings`, `Department`, `Program`, `AcademicTerm`, `Course`,
`CourseAssignment`, `Schedule`, `ScheduleSlot`, `BreakPolicy`, `WorkloadTarget`,
`InstructorDailyMetric`, `InstructorWeeklyMetric`, `UniversityDailyMetric`.

**Nullable (`String?`)** — deliberately, each for a stated reason:

| Model | Why nullable |
|---|---|
| `User` | An `ADMIN` is global and has no tenant |
| `AiInsight` | `PLATFORM`-scoped insights have no university |
| `AuditLog` | A global admin action must still be recorded. It was previously required, which made the logger silently drop every admin action — the audit trail was blind to the most privileged actor |
| `Notification`, `ReportingPeriod`, `ReportJob` | Nullable in the schema; no explanatory comment present |

**No `universityId` at all**: `ActivityType` (platform-wide taxonomy),
`Session` (tenancy derived transitively through `User`), `MetricsJobRun` (a
global job record spanning many universities per run).

### Structural enforcement, beyond application code

Two database-level invariants make tenant mixing impossible rather than merely
forbidden:

1. **CHECK constraint `user_role_tenant_binding`** (migration
   `20260811075500_phase1_invariants`), verified live:
   `CHECK (role = 'ADMIN' AND "universityId" IS NULL OR role <> 'ADMIN' AND "universityId" IS NOT NULL)`
2. **Composite foreign key** on both `Manager` and `Instructor`:
   `(userId, universityId) → User(id, universityId)`, backed by
   `User @@unique([id, universityId])`. A profile therefore cannot sit in a
   different university than its own user account.

**Row-Level Security was evaluated and deliberately not adopted.** RLS requires
the tenant on the session via `SET LOCAL` inside the query's transaction.
Under pooled connections a `SET LOCAL` that leaks past its transaction applies
the wrong tenant — worse than no RLS. Application-level isolation is mandatory
regardless and is what the test suite exercises. RLS becomes attractive only if
raw SQL access outside Prisma is introduced.

## 5. Pagination indexes

Added when server-side pagination was introduced, and only after measuring the
actual `WHERE … ORDER BY … LIMIT … OFFSET` shapes the new endpoints issue.
Migration `20260814065256_pagination_indexes_activitylog_instructor`.

| Index | Why | Measured (pagination-pass dataset) |
|---|---|---|
| `ActivityLog (instructorId, startTime)` | The activities route filters on `instructorId` but orders by `startTime`. The existing `(instructorId, workDate)` covered only the filter, so Postgres sorted the instructor's entire matching set before applying `LIMIT` | **12.8 ms → 0.07 ms** on page one, 20k rows for one instructor |
| `Instructor (universityId, createdAt)` | The instructor list's default order is `createdAt`, filtered by tenant | **6.6 ms → 0.07 ms**, 20,514-row table |
| `Instructor (createdAt)` | The admin case has no tenant filter; a composite cannot serve an `ORDER BY` on its second column without an equality predicate on the first | **7.4 ms → 0.06 ms**, same table |

**Candidates measured and deliberately rejected** — `Deliverable`,
`University`'s search, `AuditLog`, `LeaveRequest`, `ScheduleSlot`, `AiInsight`,
`UniversityDailyMetric`. Each was checked against the real query shape and left
alone. Notably, `University` search uses a leading-wildcard `ILIKE '%term%'`,
which no btree index can serve — a trigram/GIN index would be required, and was
judged unjustified at this table's realistic size.

**Known limitation of OFFSET pagination.** Deep offsets cost O(offset)
regardless of indexing, because Postgres must walk and discard the skipped rows.
Measured at offset 15,000: ~10.5 ms → ~9.4 ms — essentially unchanged by the
index. Page one, the overwhelmingly common case, is where the gain is. A true
fix is cursor/keyset pagination, which is **not implemented**.

## 6. Dashboard query performance (Phase-10 dataset)

Warm-cache, best of three, measured across two sessions against the 3.9M-row
dataset. Where sessions disagreed a range is given — single samples on a laptop
under Docker are noisy. **Not re-measured since.**

| Query | Before | After | Plan change |
|---|---:|---:|---|
| Manager, one university, one week | 44.5 ms | **1.2–2.2 ms** | Bitmap scan over 39k rows → index scan over exactly 3k |
| Manager, one university, one month | 6.0 ms | **2.2 ms** | Heap scan → Index Only Scan |
| Instructor, own week | 0.15–1.3 ms | unchanged | Already correctly indexed |
| Admin, platform-wide week | 28–65 ms warm (399 ms cold) | **0.8–1.3 ms** | Parallel Seq Scan → summary table |

`Rows Removed by Filter` on the manager query went from 36,000 to zero. That
structural change matters more than any single timing.

The admin figure needs care: the *before* number degrades linearly with total
platform activity, while the *after* number depends only on universities × days.
The gap widens with scale.

## 7. Aggregation and rollup

The admin query was a sequential scan at *100* universities. No index fixes a
full-platform aggregate, so the read path changes rather than the index set.

```
ActivityLog (source of truth)
   ↓ rollupUniversityDaily()  ← calls the SAME analytics engine as the dashboards
InstructorDailyMetric · InstructorWeeklyMetric · UniversityDailyMetric
   ↓
admin overview · instructor metrics
   ↓ drill-down goes back to ActivityLog
```

**The rollup does not reimplement the workload maths.** It calls
`computeAnalytics`, so a summary row cannot disagree with a drill-down into the
activity that produced it. Reimplementing the maths for speed is precisely how
reporting and dashboard numbers diverged in this codebase before.

Properties, all covered by tests:

- **Idempotent** — upserts on `(instructorId, metricDate)` /
  `(universityId, metricDate)`, so a late-submitted activity corrects the day
  rather than duplicating it.
- **A cache, not a second truth** — rebuildable from `ActivityLog` at any time.
- **Preserves `MISSING_DATA`** — a working day with no records stays distinct
  from a day measured as unutilised, through the summary layer.
- **Weekly is derived from daily**, so a week is by construction the sum of its
  days rather than a third independent computation.

**Two open defects in the weekly path**, recorded here rather than left to the
verification report alone: a rollup over a partial window writes the partial sum
as if it were the whole week (the code widens the date range but sums only the
daily rows that exist), and `minutesByActivityType` is hardcoded `{}` on the
weekly row despite the schema declaring it. See
[VERIFICATION-REPORT.md](VERIFICATION-REPORT.md) §15.

Chunked writes (500 rows per transaction) so the job never holds long locks on a
table dashboards are reading. Scheduling, leases, and the trailing-window
rationale are documented in the README's "Metric rollup" section.

## 8. ActivityLog: append-only, and one undeclared index

`ActivityLog` is an event ledger. It carries `createdBy`, `source`, `createdAt`
and `updatedAt`, but **no `deletedAt`** — while six other models do carry one
(`User`, `University`, `Deliverable`, `Department`, `Program`, `Course`). Soft
delete was applied selectively to *entities*, not to *events*.

There are **no `PATCH`, `PUT` or `DELETE` endpoints** for activities; the route
exports only `POST` and `GET`. See the README's "Known gaps" for the product
decision behind that, and §14 below.

### An index that exists in the database but not in schema.prisma

The once-per-day rule is enforced by:

```sql
CREATE UNIQUE INDEX "ActivityLog_once_per_day_idx"
  ON "ActivityLog"("instructorId", "workDate", "activityTypeId")
  WHERE ("isOncePerDay" = true);
```

It was created by raw SQL in migration `20260811090452_phase3_activity_logs` and
is confirmed present in the live database. It is **not declared anywhere in
`prisma/schema.prisma`**.

Consequences, stated plainly because they are easy to trip over:

- The constraint is genuinely enforced, and is covered by a migration, so a
  database built from migrations has it.
- `prisma migrate diff` reports **no drift** in either direction — Prisma's diff
  engine does not surface this partial index as a difference. "No drift" here
  means "no drift in what Prisma tracks", not byte-for-byte parity.
- **Anyone reading only `schema.prisma` would miss this invariant.** That is the
  actual risk, and the reason it is called out here.

Application code enforces the same rule independently (returning
`DUPLICATE_ONCE_PER_DAY_ACTIVITY`), so the index is a second line of defence
rather than the only one.

**The phase-10 migration is safe against populated tables.** Every column that
ends up `NOT NULL` was added nullable → backfilled from real data →
constrained. `DeliverableLog.date` → `workDate` is a **RENAME**; the generator
originally emitted `DROP COLUMN` + `ADD COLUMN`, which would have destroyed every
logged entry.

dominated by building the three composite indexes. At 10× the data expect
roughly 10× that, and the index builds should move to
`CREATE INDEX CONCURRENTLY` outside a transaction.

## 11. Scale strategy and limitations

**Now.** PostgreSQL + Prisma, query-driven indexes, daily rollups. On the
Phase-10 dataset the slowest dashboard path measured 2.2 ms at 3.9M rows.

**Partitioning — designed for, not applied.** `ActivityLog` and `AuditLog` are
the time-series candidates and both carry a `DATE` column suited to RANGE
partitioning. Not applied because at 3.9M rows the indexed queries run in
single-digit milliseconds. The trigger to revisit: `ActivityLog` past ~50M rows,
or index maintenance becoming disruptive. Nothing in the schema blocks it — the
partition key already exists.

**Projected growth** (projection, not a measurement). Raw activity scales with
instructors × days; the summary scales with universities × days. At 5,000
universities the raw table grows ~50× (to ~195M rows) while
`UniversityDailyMetric` grows to ~325k rows. That divergence is the point of the
aggregation layer.

**`/api/admin/overview` response size is still O(N) in universities.** Its
*query count* is now O(1) for the common case (see §12), but the route fetches
every university row with no `take`/`skip`/`cursor` and returns one object per
university. The endpoint has no pagination mechanism. Confirmed by reading the
route. This is the next thing to hit as the platform's university count grows.

## 12. Admin overview: N+1 removal

The endpoint previously issued **4 queries per university** — aggregate,
coverage scan, active-instructor count, activity-type breakdown — on top of a
handful of fixed queries that do not scale with N.

Universities are now grouped by their resolved `{from, to}` reporting period, and
each group runs one batched `groupBy`/`findMany({where: {universityId: {in: […]}}})`
per concern. The active-instructor count is period-independent and is batched
once across every university regardless of grouping.

Measured with Prisma's own query-event log against real seeded rows, isolating
the per-university portion:

| Universities | Before | After |
|---:|---:|---:|
| 3 | 12 | 4 |
| 10 | 40 | 4 |
| 100 | 400 | 4 |

**When is this O(1)?** When `?from=` and `?to=` are both supplied, every
university resolves to the identical period → one group → constant query count.
Only when both are omitted does the per-timezone "trailing 7 days" default apply,
which can split universities across at most one group per distinct timezone —
O(number of distinct resolved periods), never O(N).

*These figures were measured when the change was made and have not been
re-measured since; the current code structure was re-read and confirmed to match
the described batching.*

## 13. Security posture at the data layer

- **Rate limiting exists**, on `POST /api/auth/login` only, keyed by **both** IP
  and account email (whichever trips first). Defaults: 30 per 5 min per IP, 10
  per 5 min per email; both env-overridable. **In-memory, per-process,
  fixed-window** — behind multiple instances the effective limit multiplies and a
  restart clears counters. The module says so itself. Bounded at 10,000 tracked
  keys with expiry eviction.
- **Sessions** store only a SHA-256 hash of an opaque 32-byte random token, never
  the token. httpOnly cookie, `sameSite=lax`, `secure` in production, 12-hour
  default TTL.
- **Passwords** use scrypt (N=2¹⁵, r=8, p=1), 64-byte key, 16-byte salt,
  `timingSafeEqual` verification, plus a dummy-hash delay on unknown accounts so
  login timing does not reveal account existence.
- **Errors never leak internals.** One centralised handler shapes every API error
  response. There are exactly **two** hand-written `catch` blocks in the API
  tree: the report-export path, which writes `error.message` to a `ReportJob`
  database column and rethrows; and the health check, which returns a `503`
  carrying no error detail. Neither returns internals to a client. Verified: a
  real triggered 500 returns
  `{"error":{"code":"INTERNAL_ERROR","message":"Something went wrong"}}` with the
  stack going to the server log only.

## 14. Not implemented

Stated plainly rather than implied:

- **Activity edit and delete.** No `PATCH`/`PUT`/`DELETE` endpoint exists. Note
  that `logActivity` accepts an `excludeActivityId` parameter designed for
  re-validating an edit, but **no caller anywhere passes it** — the capability is
  half-built in the logger with no HTTP surface. The product decision is recorded
  in the README's "Known gaps".
- **XLSX and PDF export.** Confirmed absent by exhaustive grep: no `xlsx`,
  `exceljs`, `pdfkit` or equivalent dependency, and no route producing either
  format. CSV only.
- **Cursor/keyset pagination.** OFFSET only; see §5.
- **Pagination on `/api/admin/overview`.** See §11.
- **`Deliverable.status` never becomes `OVERDUE` or `CANCELLED`.** Both values
  exist in the `DeliverableStatus` enum, but no code path writes either — the
  only writers set `NOT_STARTED`, `IN_PROGRESS` or `COMPLETED`. "Overdue" is
  computed ad hoc where needed (`dueDate < now`) and never persisted. Frontend
  code that filters on `status === "OVERDUE"` therefore cannot match a real row.
- **Partitioning, read replicas, RLS** — reasoned about above, not applied.
- **Redis / BullMQ.** The rollup runs on an in-process scheduler with a database
  lease. Sufficient for a single long-running Node process; a queue becomes
  necessary if deployed serverless or if a rollup outgrows one tick.
- **UUIDv7.** IDs remain `cuid()` — already non-sequential and
  collision-resistant. Rewriting every key across 31 tables is a high-risk
  migration for a stylistic gain.
- **`User.firstName`/`lastName`.** Kept as a single `name` — splitting names is a
  well-known internationalisation failure. A deliberate deviation.
- **Academic and scheduling tables have partial API coverage.** The schema,
  indexes and constraints exist; not every table has endpoints.
- **Load testing beyond the Phase-10 dataset.** Measured at 100 universities /
  10,000 instructors / 3.9M activities. Larger runs are projected from query
  plans, not demonstrated.
